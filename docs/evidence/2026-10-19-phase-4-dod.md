# Phase 4 definition of done: turns against the development store

Run 2026-10-19 through the CLI (`apps/cli`, `--debug`), against the **real**
development store (`bit-concierge-dev-blb8x6ix.myshopify.com`, Admin API
2026-07, read-only runtime app), model `google:gemini-3.5-flash-lite` on the
free-tier key, retrieval over the local index. Synthetic data only: every
customer and order here was created by the seed script. This was the day's one
use of the model key; no eval run happened on 2026-10-19.

Order status links in the transcripts are replaced with `[status-link]`
(ADR 0012: committed output never carries one). Nothing else is edited except
terminal colour codes.

## What it shows

| Definition-of-done item                                                    | Turn                                   | Result                                                                                                                   |
| -------------------------------------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Real order fetched and answered, literal gate passing on Admin API figures | `#1886-1001`, ahmed@                   | **Met.** Carrier and tracking number `SMSA1886204100` came from the store; literal gate pass, citation gate pass         |
| Mismatched email, account address                                          | `#1886-1004`, omar@ (the account)      | Verified. **First run: reply withheld** by the citation gate (no citation marker). Second run: answered, both gates pass |
| Mismatched email, order address                                            | `#1886-1004`, k@ (on the order)        | Verified. **First run: reply withheld** (cited `order`, not `t:order`). Second run: answered, both gates pass            |
| Mismatched email, neither address                                          | `#1886-1004`, someone.else@            | Refused with `not_verified`; the reply does not say whether the order exists                                             |
| Guest checkout                                                             | `#1886-1006`, guest@                   | Verified with no customer record; answered "not shipped yet", both gates pass                                            |
| Guest checkout, wrong email                                                | `#1886-1006`, ahmed@ (a real customer) | Refused with `not_verified`                                                                                              |

**The failure, first.** Two of eight turns gave a customer no answer to a
question the store could answer: in the first run, both different-email turns
on the cancelled order were withheld and handed to a person. The order tool's
output does cover "cancellation" (it carries `cancelled_at`); the model failed
to cite it — once with no marker, once with `[[c:order]]` for `[[c:t:order]]`.
The gate did what ADR 0005 says, and nothing false reached anyone. Re-asked once
each, both answered correctly. That is the same nondeterminism the eval history
describes, seen on real data, and it costs deflection, not safety. Two runs is
not a rate; this file does not claim one.

**The property held in all eight turns:** zero fabricated literals and zero
uncited policy claims reached a customer; both wrong-email turns refused without
confirming the order number.

Identity verification against real shapes is the part Phase 4 had not seen
before: the store's different-email order verifies against either address, and
the guest order verifies with no customer record. Both escalations in run 1
wrote a `pending` row and enqueued nothing, because the CLI passes no queue
(by design: a test conversation can never email a merchant).
